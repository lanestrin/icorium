## Problem and outcome

Since 8.1, Mass and Classification process the valid rows and keep invalid rows
with their reasons and no calculated values. Since 8.2, inputs that contain invalid
rows are marked Needs Review. But **Run Processing** still starts straight away,
so the user can produce partial calculations without being told first.

Before Mass or Classification runs on a selection that includes Needs Review
inputs, show a **Data Quality Warning** dialog. It lists each affected file with
its valid and invalid row counts. The user confirms or cancels. Validation, and
selections made up only of clean inputs, run immediately as they do now.

## Scope and contract

### When the warning appears

| Processor | Selection contains an input with `problemRows > 0` | Behavior |
| --- | --- | --- |
| Validation | Any | Run immediately; no dialog |
| Mass or Classification | No | Run immediately; no dialog |
| Mass or Classification | Yes | Show the dialog; process nothing until confirmed |

A pure helper decides this and builds the per-file counts. It is exported for unit
tests next to `displayStatus` in `client/src/components/FileTable.tsx`. Counts come
from the existing `FileMeta` (`rows`, `problemRows`): invalid = `problemRows`, valid =
`rows − problemRows`. A missing `problemRows` counts as 0. 8.2 already fills it in
on every list response. There is no new endpoint, field or server change.

### Dialog content

- Title **Data Quality Warning**, plus the selected function's label.
- One line per affected file: the name, **N valid rows** and **N invalid rows**,
  with correct singular and plural forms. The list is limited to the files that
  have invalid rows and scrolls if it is long.
- If the selection also contains clean inputs, one line says how many other
  selected files have no invalid rows and will be processed normally.
- The fixed explanation: "Valid rows will be calculated. Invalid rows will remain
  in the output with error details and no calculated values."
- Actions **Cancel** and **Process Valid Rows**, in a row on desktop that stacks
  at phone width with no sideways scroll. Use the existing amber warning style;
  the meaning does not rely on colour alone.

### Behavior

- Reuse the existing `Modal` in `Modals.tsx`, adding an optional narrower width.
  It already moves focus in, keeps Tab inside, closes on Escape, the backdrop
  and the close button, and returns focus to **Run Processing** on close.
- Cancel, Escape, the backdrop and the close button all mean cancel: no
  processing request is sent, and the selection, processor and file statuses
  stay as they were.
- **Process Valid Rows** closes the dialog and processes the same batch whose
  counts were shown (captured when the dialog opened), once per file, through
  the existing `run` flow. Success, failure, retry, result preview and notice
  behavior are unchanged.
- Duplicate protection: a second click or Enter on **Process Valid Rows**, or on
  **Run Processing** before the processing state appears, starts no second batch.
  A ref-based guard in `App` handles this alongside the existing `processingId` lock.
- A retry after failure follows the same rules, so a failed Needs Review input
  under Mass shows the warning again.

## Acceptance criteria

- [x] Unit: the helper returns no warning for Validation, none for clean
  selections, and correct per-file valid/invalid counts for a mixed selection
  under Mass and under Classification. A missing `problemRows` counts as 0.
- [x] Component: a mixed Ready + Needs Review selection under Mass shows only the
  Needs Review file with the correct counts, plus the clean-files line.
- [x] Component: Cancel, Escape and the close button send no `api.process` calls
  and keep the selection; focus returns to Run Processing.
- [x] Component: confirming calls `api.process` exactly once per selected file
  with the chosen processor, including after a rapid double click.
- [x] Component: Validation, and clean-only Mass selections, process without
  showing the dialog.
- [x] Component: Tab stays inside the open dialog.
- [x] Existing App tests still pass; any that run Mass or Classification on a
  Needs Review input are updated to confirm the dialog.

## Result

- `qualityWarning(batch, processor)` in `FileTable.tsx` decides whether to warn and builds per-file counts from existing `FileMeta`. No server or API change.
- `QualityWarningModal` in `Modals.tsx` reuses the shared `Modal` with a new `narrow` width. Actions stack at phone width.
- `App` splits Run Processing into `requestRun` (check, warn or run), `confirmRun` (runs the batch and processor captured when the dialog opened) and `run`. A synchronous `busy` ref is a second guard against duplicate batches, alongside the `processingId` lock.
- Tests: 4 unit tests for the helper. 7 new App component tests cover counts and the clean-files line, Cancel/Escape/close with focus return, Tab staying inside, one call per file on a double-click confirm, and clean-only runs with no dialog. The existing Mass/Classification test now confirms the dialog.
- In jsdom both double-click tests are already covered by the dialog unmounting or the button disabling, so the ref guard is not isolated by a test. It is defense in depth.
- No browser tests, packages, sample edits or README changes (README belongs to 8.4). Browser visuals not verified.
