# Feature: R-32 + R-125 over 50% flag

**From build-plan:** feature 9.11
**Build attempt:** 1
**Status:** verified
**Branch:** `feature/9.11-r32-r125-over-50-flag`

## Goal

Batch Classification results get a Yes/No column, `r32_r125_over_50`, that
marks rows where R-32 + R-125 is above 50%. The person asked for this on
2026-11-12. They chose a separate column instead of a new blend class because
every sample row has R-32 + R-125 between 62% and 77%, so a blend class would
have taken over every row or every Balanced row. `blend_class` is unchanged.

## In scope

- A new generated column `r32_r125_over_50` in Classification results, placed
  after `dominant_component` and before `processing_status`.
- Values: `Yes` when R-32 + R-125 > 50 (strictly greater), `No` otherwise, and
  blank on invalid rows (as Mass leaves its masses blank).
- Classification exports made before this change, with or without
  `result_id`, still upload and are still detected as Classification results.
- Those older exports still compare with new Classification results. The
  comparison leaves out `r32_r125_over_50` unless every compared file has it.
- A readable comparison metric label for the new column.
- README updates where it describes the Classification columns and rules.

## Out of scope

- Any change to `blend_class`, `DEMO_CLASS_RULES` or `dominant_component`.
- Validation and Mass results, the CSV generator and the sample CSVs.
- Comparing the 8.1-era legacy suffixes (`blend_class`, `dominant_component`
  with no status columns) with current results. That stays refused with the
  existing "Regenerate the older result" message.
- A threshold setting. 50% is a fixed demo rule, like `DEMO_CLASS_RULES`.
- The Architecture page. It names no Classification columns (checked with grep),
  so its content does not change.

## Build loop

`workflow.stepReview` is `feature`: build every step, then produce one review

commit and PR drafts, and only the person's `/approve` commits and pushes.
The person merges.

## Build steps

- [x] **Step 1 - Generate the column** - In
  `server/src/processing/index.ts`, add `r32_r125_over_50` to
  `processors.classification.columns` after `dominant_component`. In `run`,
  return `''` for invalid rows. For valid rows return
  `round(n.r32! + n.r125!, 3) > 50 ? 'Yes' : 'No'`. The rounding stops float
  noise such as 25.1 + 24.9 from reading as just over 50. Keep the 50% threshold
  as a named demo constant next to `DEMO_CLASS_RULES`. Update the existing tests
  that list Classification columns or row values. *Done when:* the core tests
  show Yes above 50, No at exactly 50, No below 50, No for 25.1 + 24.9, blank
  on invalid rows, and an unchanged `blend_class` for the same rows.
- [x] **Step 2 - Recognise pre-9.11 exports** - In `detectResult`, also
  accept Classification's previous column set
  `[result_id, blend_class, dominant_component, processing_status, validation_errors]`,
  and the same set without `result_id`. Return that set as `generatedColumns`.
  This sits next to the existing `LEGACY_COLUMNS` handling and uses no new
  mechanism. Linking (`matchesInput`) and File ID stamping work unchanged
  because they read `generatedColumns`. *Done when:* the core tests detect the
  new set, both previous sets and the 8.1 legacy set. A partial or extended
  suffix is still undetected. The API test uploads a pre-9.11 export
  with `result_id`, gets `processor: 'classification'` with the previous
  `generatedColumns`, and links it to its original when the data matches.
- [x] **Step 3 - Compare old with new** - In `compareResults`
  (`server/src/lib/compare.ts`), when some but not all files have
  `r32_r125_over_50`, drop it from every file's function columns before the
  schema check. Files that differ in any other way still get the existing 400.
  *Done when:* the API test compares a pre-9.11 Classification upload with a
  fresh Classification result (either order) and gets 200 with the columns
  `blend_class`, `dominant_component`, `processing_status` and
  `validation_errors`. Two new results compare with `r32_r125_over_50` as a
  category column. The existing legacy-rejection tests still pass.
- [x] **Step 4 - Label and docs** - In `client/src/lib/compare-view.ts`, make
  `metricLabel('r32_r125_over_50')` return `R32 + R125 over 50%`. Other names
  keep their current labels. Update the README: the results paragraph (invalid
  Classification rows also leave the flag blank), the classification rule
  sentence, and the constants table. *Done when:* the compare-view unit test
  covers the new label and the existing labels, and `npm run verify` passes.

## Data / contracts

- **Result CSV (persisted, downloaded, re-uploaded):** new Classification
  results end with
  `result_id, blend_class, dominant_component, r32_r125_over_50, processing_status, validation_errors`.
  The value is the text `Yes`, `No` or empty. Every original column stays,
  as before.
- **Stored results are not rewritten.** Results already saved in
  `server/data/` keep their old columns and `generatedColumns`. They compare
  with new results through Step 3. Re-running Classification with `replace: true`
  regenerates a result with the new column and keeps its ID.
- **Source-column collision:** an input that already has a column named
  `r32_r125_over_50` gets the existing 400 from `processRows` that names it.
- **`GET /api/compare`:** the response shape is unchanged. The flag column
  appears as a `category` column only when every compared file has it.
- No change to File IDs, routes, `FileMeta` fields or limits.
