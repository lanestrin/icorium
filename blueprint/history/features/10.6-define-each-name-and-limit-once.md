# Feature: Define each name and limit once

**From build-plan:** feature 10.6
**Build attempt:** 1
**Branch:** `refactor/single-source-names-and-limits`
**Status:** verified

## Goal

Each processing-function name, generator limit, status option and generator
validation message is defined in one place, so adding a processing function or
changing a limit needs one edit. Behaviour and every user-visible message stay
exactly as they are.

## In scope

1. **Processing functions.** `PROCESSORS` in `shared/types.ts` becomes the only
   list of function ids and names.
   - Add a `tableLabel` field to each entry with today's `FUNCTION_LABEL` text:
     `Validation`, `Mass Calculation`, `Classification`. Delete `FUNCTION_LABEL`
     from `client/src/components/FileTable.tsx`; `processingFunction` reads
     `tableLabel`.
   - Derive the Zod enum in `server/src/routes/files.ts` (`processor:`) from
     `PROCESSORS.map((p) => p.id)` instead of the literal list.
   - The Processing Function filter in `client/src/App.tsx` filters by id, not by
     label: option values are `original` and each processor id, option text stays
     `Original` and each `tableLabel`. Replace `PROCESSING_FUNCTIONS` with a list of
     `{ value, label }` built from `PROCESSORS`. The filter matches a file when its
     function id (`original` for inputs, `processor` for results) equals the value.
     A result with no `processor` matches only `All` (as today, since `—` was never
     an option).
2. **Generator limits.** Move `GENERATOR_MAX_ROWS` (5000) and `GENERATOR_MAX_FILES`
   (10) from `server/src/lib/generate.ts` to `shared/types.ts`, beside
   `COMPARE_MAX`. `client/src/components/GeneratorPage.tsx` imports them and drops
   its own `MAX_ROWS` / `MAX_FILES` and the "kept in step" comment. Update the
   path in `client/src/architecture-content.test.ts` (line ~55), which currently
   reads the limits from `generate.ts`.
3. **Status filter options.** In `client/src/components/FileTable.tsx`, define one
   `STATUSES` list (`Ready`, `Needs Review`, `Processing`, `Processed`, `Error`, in
   today's order) and derive the `Status` type from it. `App.tsx` builds the Status
   filter options from that list.
4. **POST-JSON helper.** In `client/src/api.ts`, add one `postJson<T>(url, body)`
   helper (method POST, `content-type: application/json`, `JSON.stringify`, then
   `json<T>`). `process`, `archive` and `generate` use it. Request bodies and error
   handling are unchanged.
5. **Generator validation messages.** The request schema in `routes/files.ts` is
   the one place that validates generator input and owns the messages.
   - Add the one check it lacks: `errorRows` must not exceed `rows`, as a Zod
     refinement with today's message, exactly:
     `Rows with errors must be a whole number from 0 to the number of rows.`
   - Remove the duplicated input checks from `generateCsv` (rows range, errorRows
     range) and `generateFiles` (file count range). Keep the
     `Could not make N different files…` error and the unknown-partner guard (the
     adapter lookup needs it; 10.7 replaces that lookup).
   - Delete the `core.test.ts` cases that pinned the removed `generateCsv` /
     `generateFiles` messages (~lines 403–411). Every API message stays covered by
     the existing table in `api.test.ts` (~846–854).
6. **Docs.** Update `CLAUDE.md` "Extending" and README's "New processing function"
   line: a new function is added to `processors` in
   `server/src/processing/index.ts` and to `PROCESSORS` in `shared/types.ts`; the
   Zod enum and the table label follow from `PROCESSORS`. The partner line is
   10.7's job and stays.

## Out of scope

- Partner adapters, `GENERATOR_PARTNERS` and `DIGITS` (10.7).
- Moving client logic between components (10.8), storage, caching or settings
  (10.9–10.12).
- Changing any label, message, limit, option order or filter behaviour.
- Browser tests.

- API request and response shapes, status codes and messages are unchanged.
  `POST /api/process` still accepts exactly `validation`, `mass`,
  `classification`.
- `POST /api/generate` rejection messages are unchanged; when several fields are
  invalid the handler still joins Zod issue messages with `; `. The `errorRows >
  rows` refinement runs only after the field checks pass, so a single-field error
  reads as today.
- No stored data changes. `PROCESSORS` gains one display field; `code` values are
  untouched.
