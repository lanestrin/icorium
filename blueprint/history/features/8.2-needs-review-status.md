## Problem and outcome

All input files currently report Ready even when their `problemRows` count is
nonzero. The table already shows a separate flagged-row tag, but its status
does not distinguish clean inputs from inputs containing invalid data.

Show **Needs Review** for inputs with invalid rows and **Ready** for clean
inputs. Both remain processable. Results stay **Processed**, including results
containing Invalid rows. Make the API, table, status filter and selection logic
agree without changing validation or adding the later warning dialog.

## Scope and contract

### Authoritative file status

Extend `FileStatus` in `shared/types.ts` with the exact value `Needs Review`.
Keep `problemRows` as the count of invalid rows, not the number of errors.
Derive counts from 8.1's shared validation rules, not from CSV status text.

| File kind | Invalid rows | Persistent status | Processing eligible |
| --- | --- | --- | --- |
| Input | 0 | Ready | Yes |
| Input | Greater than 0 | Needs Review | Yes |
| Current or legacy result | Any | Processed | No |

Apply this to newly uploaded inputs, initial sample seeding, and existing
saved metadata returned by the list endpoint. Result detection and comparison
compatibility remain as implemented in 8.1.

For old metadata, fill missing `problemRows` using shared validation and
reconcile input status even when the count is already present. Persist only
metadata fields that need changing through `storage.patch`. Known counts may
be reused because stored CSV contents are immutable through the app. Do not
recalculate every file on every refresh, rewrite CSV bytes, change IDs/times,
delete data, or require a reset. A stale Ready status must not survive solely
because the count already exists. Do not convert Processed results to inputs.

`GET /api/files` still lists all files; filtering remains client-side. The
upload response and next list response must agree. No endpoint, query
parameter, new dependency or storage format version is needed.

### Table and invalid-row tag

- Add a Needs Review badge using the existing rounded badge style, an amber
  warning icon and visible text. Match the existing design/reference; no
  layout redesign. Meaning must not depend on color alone.
- Replace the existing flagged tag wording with **N invalid** for any file
  whose `problemRows` is greater than zero, including Processed results.
  Give assistive technology the full meaning (for example "1 invalid row" or
  "2 invalid rows"); retain a helpful explanation pointing to Preview.
- Clean inputs and clean results have no invalid-row tag. Preview/download
  actions and existing per-row problem details remain available.

### Selection and processing feedback

- Explicitly recognize Ready and Needs Review as input statuses wherever the
  current UI checks `status === 'Ready'`: App's selected inputs, table row and
  checkbox eligibility, checked highlighting, and select-all input collection.
  Keep this rule consistent without introducing a new state-management layer.
- Mixed Ready/Needs Review selections run with the selected processor. Results
  remain unselectable by row click, checkbox and select-all; the API continues
  to reject result-file processing. Input status does not block any processor.
- Preserve the existing processing lock and transient display precedence:
  Processing while running, Error on request failure, otherwise persistent
  Ready/Needs Review/Processed status. These transient states are not persisted.
  Invalid input data by itself means Needs Review, not a failed request.
- Preserve retry behavior: failed inputs stay checked; successful inputs are
  cleared. Processing does not repair a source CSV, so an invalid input returns
  to Needs Review after success. Its new result is Processed with N invalid.

### Filtering

- Status options: All Statuses, Ready, Needs Review, Processing, Processed,
  Error. Use the same displayed-status function for badge and filter membership.
- Ready excludes Needs Review; Needs Review excludes clean inputs and all
  results; Processed includes results regardless of invalid counts.
- Search and date constraints still combine with the status filter. Clear
  filters resets status to All and clears the other constraints.
- Preserve the existing selection policy: changing filters does not deselect
  hidden inputs. Select-all toggles eligible visible inputs only, leaving
  hidden selections untouched. The processing panel continues to list all
  selected input names so a filtered-out selection is not silently hidden
  from the user before Run Processing.
