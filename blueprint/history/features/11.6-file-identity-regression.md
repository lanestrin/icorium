# Feature: File identity regression

**From build-plan:** feature 11.6
**Build attempt:** 1
**Branch:** `test/11.6-file-identity-regression`
**Status:** verified

## Goal

Lock in the M11 identity contract with one end-to-end regression per layer.
Files that share a filename never collide. Every action is keyed by the full
File ID. One original's re-run never touches another original's result. The
ID relationships survive archive, restore, download, re-upload and comparison,
and imported results follow the 11.7 lineage rule. Tests only: no product code
changes are expected.

## In scope

- **Server API regression** (`server/src/api.test.ts`, a new
  `describe('file identity regression')`), run once for each function
  (`it.each` over `validation`, `mass`, `classification`, so all three
  suffixes `-V`, `-M`, `-C` are covered):
  1. **Same-name uploads.** Upload three CSVs all named `identity.csv` with
     different contents: `partner_a_baseline.csv`, `partner_a_followup.csv`,
     and `partner_a_baseline.csv` again. They get three distinct, consecutive
     base IDs, all keep the name `identity.csv`, and each stored `file_id`
     equals its own ID.
  2. **Separate results.** Processing each gives `<id>-<code>`. The three
     results are distinct files with the same name
     (`result_identity_<function>.csv`), and each `result_id` and `file_id`
     column holds its own IDs. The first and second results differ in content.
  3. **Unconfirmed repeat ("cancel" on the server).** Re-running the first
     input without `replace` answers 409 naming `<first>-<code>`. All three
     results are unchanged byte for byte.
  4. **Confirmed replacement of exactly one.** With `replace: true`, the first
     result keeps its ID. The list holds exactly one file with that ID, and the
     other two results are unchanged byte for byte.
  5. **Archive and restore by ID.** Archiving `<second>-<code>` flags only that
     file, even though another result shares its name. Restoring it clears the
     flag and changes nothing else.
  6. **Download.** Each result downloads its own bytes under the shared
     filename label. Downloads of same-named results differ, and each carries
     its own `result_id`.
  7. **Re-upload (11.7 rule).**
     - An unchanged download of the first result re-uploads with a new base ID
       plus the same code, `imported`, `sourceId` = the first input, and
       `importedFrom` = the first input.
     - The second result's download with one original value edited re-uploads
       unlinked, with `importedFrom` = the second input and no `sourceId`.
     - Neither upload replaces or renames an existing file.
  8. **Comparison by full ID.** Comparing two of the same-named results returns
     `files` with exactly those IDs, in request order. Comparing five (the three
     results and both imports) returns five files with five distinct IDs in
     request order. Two of them share a name, and the comparison still answers
     200.
  9. **No lookup by name.** `GET /api/files/identity.csv/rows`, `…/download`
     and processing `identity.csv` all answer 404.
- **Blob storage regression** (`server/src/blob-storage.test.ts`), following
  the existing fresh-API-instance pattern. On one instance, upload two
  same-named CSVs and process both. From a fresh second instance, list,
  preview and download each result by its ID: both exist with distinct IDs
  and their own contents.
- **Client regression** (`client/src/App.test.tsx`, a new
  `describe('file identity regression')` with mocked `api`). Two inputs named
  `data.csv` (`101010`, `101011`) and their Validation results (`101010-V`,
  `101011-V`), which share a name:
  1. Select `101010` and Run Processing. The Replace dialog names `101010` and
     `101010-V`, and never `101011-V`. **Cancel** sends nothing.
  2. Run again and choose **Run & Replace**. `api.process` is called exactly
     once, with `('101010', 'validation', true)`.
  3. Archive `101011-V` from the selection bar. `api.archive` is called with
     `['101011-V']` only.
  4. Select both results and Compare. `api.compare` is called with
     `['101010-V', '101011-V']`, and the dashboard chips show both IDs.
- Record the outcome on the 11.6 line of `blueprint/build-plan.md` at

## Data / contracts

No contract changes. The tests assert the existing contracts:
- File ID formats `^\d{6}$` and `^\d{6}-[VMC]$`.
- `POST /api/process` returns 409 `ReplaceConflict` without `replace: true`.
- `POST /api/files/archive` takes `{ ids, archived }`.
- `GET /api/compare?ids=` returns `CompareResult.files` in request order.
- The 11.7 lineage fields `sourceId` and `importedFrom`.
