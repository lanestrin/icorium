# Feature: Atomic result create

**From build-plan:** feature 11.3a
**Build attempt:** 1
**Branch:** `fix/11.3a-atomic-result-create`
**Status:** verified

## Goal

Close the race in `POST /api/process` between "this result does not exist" and
writing it. Today the route checks for the result (`findFile`), then awaits the
input read, then saves with an unconditional overwrite (`storage.put`). Two first
runs of the same function on the same input can both pass the check and both
write, and an unconfirmed request can overwrite a result created moments earlier.
After this item, a write without `replace: true` is create-if-absent: if another
request created the result first, the request gets the same 409 `ReplaceConflict`
as a normal refused re-run and nothing is changed.

## In scope

- A create-if-absent write at an exact File ID in both storage backends.
- `POST /api/process` uses it for every request without `replace: true`, and
  turns a lost race into the existing 409 `ReplaceConflict`.
- Confirmed replacement (`replace: true`) keeps its current overwrite semantics,
  documented explicitly (see Data / contracts).
- README limitation line and the Architecture page storage text updated to match.

## Out of scope

- The confirmation dialog and client double-submit protection (11.4).
- Showing File IDs in the UI (11.5) and the identity regression suite (11.6).
- Version or ETag protection for confirmed replacements (decided: last confirmed
  write wins, see Data / contracts).
- The storage interface refactor (10.9), including converting local storage to
  `fs/promises`, atomic `meta.json` writes and sharing a declared interface.
- Any change to upload ID allocation (`create`) or sample seeding (`seed`).

## Build steps

- [x] **1. Create-if-absent storage write.** Add `createAt(id, input)` to both
  backends, beside `put`:
  - Local (`server/src/lib/storage.ts`): if a file with that exact ID exists,
    return `undefined` and change nothing; otherwise behave exactly like `put`.
    The check and the write run in one synchronous step, so no other request can
    run between them in this process.
  - Blob (`server/src/lib/blob-storage.ts`): write `files/<id>.json` with the
    existing `createOnce` (`allowOverwrite: false`); return the new `FileMeta`,
    or `undefined` when the object already existed. Other SDK failures propagate.
  - Both reject a non-File-ID the same way their `put` does.

  **Done when:** unit tests show, for each backend, that `createAt` saves a new
  ID, returns `undefined` for an existing ID while leaving its metadata and text

- [x] **2. Use it in `POST /api/process`.** In `server/src/routes/files.ts`:

## Data / contracts

- **`POST /api/process`** request is unchanged: `{ fileId, processor, replace? }`
  (`replace` defaults to `false`).
- **Responses:** 200 with the result `FileMeta` (unchanged). 409 with
  `ReplaceConflict` `{ message, existing: { id, name, archived } }`, message
  `"<function label> has already been run for file <input id>. Confirm to replace
  the existing result <result id>."`, now returned both by the early check and by
  a lost create race. Other errors (400 result/archived input, 404) unchanged.
- **Guarantee:** a request without `replace: true` never modifies an existing
  result, including one created by a concurrent request.
- **Confirmed replacement semantics (decided, documented):** `replace: true`
  overwrites unconditionally. Two confirmed replacements of the same result at
  once both write; the last write is kept, under the same File ID. Both computed
  the result from the same stored input, so the content is the same apart from
  `uploadedAt`. Preventing duplicate submissions from the UI is 11.4.
- **Storage:** `createAt(id, input: NewFile): FileMeta | undefined` (local) and
  `Promise<FileMeta | undefined>` (Blob). Stored shape is unchanged
  (local `files/<id>.csv` + `meta.json`; Blob `files/<id>.json` with
  `{ meta, text }`). No migration.

## Notes for the AI

- Keep the early `findFile` check: it is the common case and avoids processing
  a large file only to be refused. `createAt` is the guarantee, not a replacement
  for the check.
- Do not add locks, queues, version fields or a new dependency. Local
  atomicity comes from the synchronous check-and-write; Blob atomicity from
  `allowOverwrite: false`.
- `createAt` on local storage should reuse `put` for the write so `uploadedAt`,
  metadata and `persist()` behave identically.
- Only `storage.ts` and `blob-storage.ts` touch storage (project rule).
- If the existing Blob `createOnce` treats a failed `put` plus a missing object
  as an error, keep that: it must not report "already exists" for an outage.
- No em dashes in docs or comments (coding standards).
