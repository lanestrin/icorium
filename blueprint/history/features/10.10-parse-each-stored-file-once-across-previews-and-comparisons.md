# Feature: Parse each stored file once across previews and comparisons

**From build-plan:** feature 10.10
**Build attempt:** 1
**Branch:** `perf/avoid-repeated-parsing`
**Status:** verified

## Goal

Paging through a file's preview reads and parses it once, and a comparison
does not validate every row a second time. Responses stay byte-for-byte the
same, and a file that was saved again (a re-run result, a replaced file) never
serves its old rows.

## In scope

1. **A small parsed-file cache in `server/src/routes/files.ts`**, created inside
   `fileRoutes` so each app instance has its own. One helper,
   `parsedFile(meta)`, returns `{ headers, rows, problems }` for a file, where
   `problems` is `findProblems(headers, rows)`.
   - **Key: File ID plus `uploadedAt`.** Every `put`, `create` and `createAt`
     sets a new `uploadedAt`, on both backends, so a saved-again file gets a new
     key. Nothing has to invalidate the cache, and it stays correct when another
     server instance replaces the file through shared Blob storage. `patch` keeps
     `uploadedAt` and does not change the CSV, so its cached rows stay valid;
     `generatedColumns` and other metadata are always read from the fresh `meta`,
     never from the cache.
   - **Bounded:** at most 10 files (`PARSED_CACHE_FILES = 10`). A hit moves the
     file to the newest place; adding an 11th drops the least recently used.
   - Cached `rows` and `problems` are shared, read-only data: the preview returns
     a `slice`, and comparison only reads them.
2. **Preview** (`GET /api/files/:id/rows`) uses `parsedFile(await storage.get(id))`.
   Paging, `totalRows`, `generatedColumns` and `problems` are unchanged.
3. **Comparison** (`GET /api/compare`) loads each file through `parsedFile` and
   uses its cached `problems` instead of calling `findProblems` again, so rows
   are validated once per file. `matchRows` still normalizes rows for batch IDs.
   Schema detection and the existing error messages are unchanged.
4. **Tests** (`server/src/api.test.ts`):
   - Paging one file reads it from storage once: with a spy on `storage.read`,
     three pages of the 250-row file call `read` once.
   - A re-run result serves its new rows: preview a result, rewrite it with
     `storage.put` (`,STALE,` as in the existing re-run test), and the next
     preview shows `STALE`. Re-run with `replace: true`, and the preview no longer
     shows `STALE`.
   - The cache is bounded: previewing 11 other files and then the first file
     reads the first file again.
   - Existing paging, preview and comparison tests pass unchanged.

## Out of scope

- Caching downloads (`GET /api/files/:id/download` returns stored text as is),
  the `/process` route, or upload parsing.
- Blob lookup cost (10.11), configurable settings (10.12): the cache size is a
  constant.
- Any change to API responses, stored data or the client.

## Data / contracts

- No API, stored-data or client change. `FileRows` and `CompareResult`
  responses are identical for the same stored file.
- The cache lives in memory per app instance and is never written anywhere.
- Worst-case memory is 10 parsed files; uploads are capped at 10 MB each.

## Testing

- Server API: read-once paging, saved-again file, bounded cache, plus all
  existing preview and comparison tests.

  141, build ok); `main` at `ddc9b92` has the identical tree.

## Notes for the AI

- Keep the helper inside `fileRoutes` (a closure over `storage` and the `Map`);
  no new module or dependency.
- A JavaScript `Map` keeps insertion order: delete and re-set an entry on a hit,
  and drop `cache.keys().next().value` when over the bound.
