## Problem and outcome

Validation and `findProblems` use file-wide checks for missing/duplicate batch
IDs. Mass and Classification currently use only field-level `issues` checks.
A row can therefore appear in the problem list and still receive calculated
mass or a classification. Output status/error columns also differ by processor.

Use one set of row errors everywhere. Retain every source row and original
value, calculate only valid rows, and append consistent status and reason
columns to every newly generated result. Keep valid calculations, units,
rounding, demo thresholds and existing endpoint shapes unchanged.

## Scope

- Compute normalized row context and all validation errors once per processing
  operation; use the same rules and deterministic error order in Validation,
  Mass, Classification and problem reporting. Preserve the lightweight existing
  modules; no new validation framework or service layer.
- Include missing/blank batch IDs and every occurrence of a duplicate normalized
  ID, in addition to the existing mass/component/total checks. IDs remain trimmed,
  case-sensitive and scoped to one file. Retain the existing positive-mass,
  finite-number, 0–100 component and inclusive ±0.5 percentage-point rules.
  Do not introduce date validation or additional chemical rules.
- New exports append the exact columns below. Remove the old generated status
  columns from new output, but preserve original partner headers and cell strings.
- Recognize current and legacy result schemas using their complete ordered
  generated-column suffix, not filenames or the two common status columns alone.
  Return the generated columns actually present in uploaded results.
- Update comparison and regression tests in the same feature so export,
  rename/re-upload and comparison still work after the schema change.
- Update README's existing output-column examples when they would become false.
  The full warning/status demo rewrite remains 8.4.

## Output contract

All listed fields are CSV strings after serialization. Original columns stay
first, in their existing order; generated columns are appended in this order:

| Function | Generated columns, in order |
| --- | --- |
| Validation | `composition_total_pct`, `processing_status`, `validation_errors` |
| Mass | `r32_mass_kg`, `r125_mass_kg`, `r134a_mass_kg`, `processing_status`, `validation_errors` |
| Classification | `blend_class`, `dominant_component`, `processing_status`, `validation_errors` |

- `processing_status` is exactly `Valid` or `Invalid`.
- `validation_errors` is empty for valid rows. For invalid rows it contains all
  applicable reasons joined with `; `, matching the corresponding problem list
  message. Preserve existing reason text where the rule is unchanged.
- Invalid Mass rows have all three calculated mass cells empty, including
  rows invalid only because of missing or duplicate IDs.
- Invalid Classification rows have `blend_class` = `Needs review` and empty
  `dominant_component`. Valid categories keep their existing `(demo)` labels.
- Validation retains its existing `composition_total_pct` diagnostic behavior;
  this feature does not invent a mass/category for an invalid row.
- Generated metadata must match the actual CSV suffix and column count. File
  names, processor IDs, replacement-on-rerun and source-file preservation stay
  unchanged. Input status remains Ready; result status remains Processed.

## Proposed compatibility and collision decisions

The approved scope includes these choices:

1. **Keep legacy reads.** Recognize the exact prior suffixes: Validation
   (`composition_total_pct`, `validation_status`, `validation_message`), Mass
   (`r32_mass_kg`, `r125_mass_kg`, `r134a_mass_kg`, `mass_status`), Classification
   (`blend_class`, `dominant_component`). Existing stored and re-uploaded legacy
   results remain Processed, previewable and downloadable without rewriting their
   bytes or pretending they contain the new fields. Legacy generated metadata
   stays tied to the old columns. Apply the same behavior after app restart.
2. **Compare matching schemas.** New/new and legacy/legacy results from the same
   function remain comparable. Mixed legacy/new results return HTTP 400 with a
   clear explanation to regenerate the older result from its original input.
   Check both sides' actual generated schema so reversing A/B cannot silently
   change the outcome. Do not recalculate imported legacy values or label them
   as if the corrected validation had produced them.
3. **Protect source columns.** If an input contains a column that the selected
   processor would append, reject processing with HTTP 400 naming the collision.
   Do not overwrite an original cell, produce duplicate output headers, or
   reject unrelated extra columns. Exact recognized results remain protected
   by the existing prohibition on processing result files.

No disk migration, automatic deletion/reset or new required setting. Old files
are historical results, not evidence that the corrected rules ran on them.
Document the new CSV schema and mixed-schema comparison restriction as a
breaking output-contract change in the eventual commit/PR (`feat!` and footer).

## Acceptance criteria

- [x] All three functions agree on which rows are Invalid and why, and their
  invalid count equals `findProblems(...).total`. Duplicate checks mark every
  occurrence; whitespace-only IDs are missing. Valid values at the rounding
  tolerance remain valid; multiple errors on one row remain visible.
- [x] For every processor, new headers equal original headers plus exactly the
  ordered suffix above; row count/order and every original cell are unchanged.
  The old generated status fields do not appear unless they were original
  noncolliding input columns. No invalid row receives calculated mass/category.
- [x] Valid kg calculations and demo classifications remain unchanged, including
  the existing rounding and deterministic dominant-component behavior.
- [x] All five unmodified samples pass through each processor. A baseline,
  A follow-up, B baseline and C baseline each have 24 Valid/1 Invalid rows;
  B follow-up has 23 Valid/2 Invalid rows because both duplicate rows are invalid.
  Synthetic fixtures additionally cover missing IDs and multiple simultaneous
  errors; never modify the sample files to make tests pass.
- [x] `POST /api/process` returns metadata for the actual new schema; preview
  and download expose the same headers and data. Re-running the same function
  replaces the prior named result while preserving the source input.
- [x] Exporting, renaming and uploading any new result preserves its processor,
  Processed status, generated columns and original content. Inputs and partial
  or misleading status suffixes are not misidentified as results.
- [x] Legacy stored and renamed/re-uploaded results remain readable, retain
  their actual generated columns and download unchanged. API regression tests
  cover persisted legacy metadata as well as fresh uploads.
- [x] New/new and legacy/legacy comparisons keep kg totals, percentage means,
  categorical counts, row differences and problem details correct. Blank invalid
  mass values are absent numeric observations, not zero-valued measurements.
  Mixed schemas fail clearly in either A/B order. Different functions, an input
  file, and identical file IDs remain rejected as before.
- [x] Source/generated name collisions fail before writing a result and name
  the conflicting columns; unrelated extra source columns round-trip unchanged.
- [x] `npm run verify` passes. Browser tests are not required or restored.
  Any manual preview/download/comparison smoke check is reported separately;
  passing automated checks alone does not establish browser behavior.

- Current exports use the agreed suffixes and retain all source rows and values.
- Legacy imports and persisted metadata remain readable without rewriting CSVs; mixed-schema comparison explains regeneration. Comparison checks the actual CSV suffixes.
- Collisions return HTTP 400 before a result is saved.
- Verification: npm run verify (server unit/API tests and client type-check/build); server type-check also run separately. See final completion report for the current test count.
- Browser tests remain removed. Manual UI checks and a separate audit were not run; API tests cover preview, download, import and comparison without establishing browser behavior.
- No dependencies, sample CSVs, storage migration, file-status UI or warning dialog changes. Existing client chunk-size warning remains.
