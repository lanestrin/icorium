# Feature: Link imported results

**From build-plan:** feature 11.7
**Build attempt:** 1
**Branch:** `feature/11.7-link-imported-results`
**Status:** verified

## Goal

When someone re-uploads a result CSV, link it to its original input only when
the evidence supports it. The CSV must name an existing original in its
`file_id` column, and its original input columns and values must match that
input exactly. Otherwise the result keeps the source ID it claimed as
provenance, but is never presented as linked. This settles the imported-result
lineage rule (decided 2026-11-11) that 11.6 uses as its acceptance case.

## In scope

- **Server, upload of a result CSV** (`POST /api/files`, the `result` branch
  in `server/src/routes/files.ts`):
  1. **Embedded source ID:** the `file_id` value when the column exists, every
     row has the same value, there is at least one row, and that value is a
     File ID (`parseFileId`). Anything else means there is no embedded source
     ID.
  2. **Link check:** the result is linked when the embedded source ID is a
     *base* ID (no code), a stored file with exactly that ID exists (archived
     included) and is an input (`isInputFile`), and the data matches (rule 3).
  3. **Match rule:** the result's *original columns* are its headers minus its
     detected `generatedColumns` and minus `result_id`. The stored input's
     columns are its headers, which include `file_id`. They match when both
     have the same set of column names in any order, the same number of rows,
     and in every row (taken in order) the same string value for each column.
  4. **Linked:** the metadata gets `sourceId` = the original's ID and
     `importedFrom` = the embedded source ID. The stored CSV keeps `file_id` =
     the original's base ID, and `result_id` is set to the new ID.
  5. **Unlinked:** no `sourceId`. `importedFrom` = the embedded source ID when
     there is one; otherwise it is omitted. `file_id` and `result_id` are
     rewritten to the new IDs, as today.
  6. **In both cases:** a new base ID plus the detected function's code,
     `imported: true`, and status `Processed`. It never takes or replaces the
     original's own result ID (`101010-V`).
  7. **Legacy exports without ID columns** are unchanged: stored exactly as
     uploaded, unlinked, no `importedFrom`.
- **Shared type:** `FileMeta.importedFrom?: string` in `shared/types.ts`,
  documented as provenance only. The comment on `imported` changes to "an
  uploaded result; linked to an original only when `sourceId` is set".
- **Client wording.** `IMPORTED_NOTE` in `FileTable.tsx` becomes a small
  function used by both the marker `title` and the preview subtitle:
  - linked (`sourceId`): pill `title` "Uploaded result file, linked to
    original input 101010."; preview subtitle ends `· Imported from 101010`
  - unlinked with `importedFrom`: `title` "Uploaded result file. It names
    101010 as its source, but that original input is not in this workspace or
    its data differs, so it is not linked."; preview subtitle ends
    `· Imported: not linked to 101010`
  - unlinked without `importedFrom`: unchanged ("Uploaded result file. Its
    original input is not linked in this workspace." / `· Imported: original
    input not linked`)
- **Docs:** the CLAUDE.md File ID rule (uploaded results), the README
  paragraph on imported results, and the Architecture page Upload flow (one
  step on how an uploaded result is linked). `architecture-content.test.ts`
  must still pass.

## Out of scope

- Renaming (not supported, decided 2026-11-11).
- Linking legacy exports that have no ID columns, or guessing a source from
  content alone, the filename or row matching.
- Grouping linked imports under their original in Sort by File ID or search.
  Their base ID is new; sort and search stay ID-based, as in 11.5.
- Treating a linked import as the original's result for re-run replacement,
  comparison eligibility or the Replace dialog. These stay keyed by full ID.
- Migrating already-stored imported results: they stay unlinked with no
  `importedFrom`.
- The 11.6 end-to-end regression.

## Data / contracts

- `FileMeta` gains optional `importedFrom: string`. It is the File ID text
  embedded in an uploaded result, already validated by `parseFileId` before it
  is stored. It is provenance only and never used to look up, link, replace or
  compare. `sourceId` keeps its meaning (the input a result came from) and is
  now also set for linked imports.
- Both storage backends persist metadata fields generically, so no storage
  change is expected. Step 2 checks this for Blob through the existing Blob
  storage test pattern if it stores a field list.
- Already-stored files have no `importedFrom` and are not migrated. Older
  metadata simply lacks the field.
- Stored CSV for a linked import: `file_id` = the original base on every row,
  `result_id` = the new full ID. For an unlinked import: both are the new IDs,
  as today.
- `POST /api/files` keeps its response shape (`FileMeta`) and its error codes.
  No new error: a failed link check is never an error, only "unlinked".
- Client renders `importedFrom` and `sourceId` as React text only.

## Notes for the AI

- The comparison is exact string equality per cell. Results keep every
  original column and value unchanged, so an untouched export matches. Do not
  normalise numbers or whitespace: an edited file must not link.
- Row order matters; column order does not, because "accounting for column
  order" means a reordered export still matches.
- `detectResult` returns the trailing generated columns. An older-format
  result may hold `result_id` outside them, so strip `result_id` explicitly
  from the original columns.
- Keep reading the source input to this one upload request. Do not add
  caching (10.10 covers parsing reuse).
- Use `findFile` for the lookup so unknown IDs are a normal "unlinked", not a
  404 response.
